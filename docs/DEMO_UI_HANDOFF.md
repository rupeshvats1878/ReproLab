# Demo UI handoff

Branch `demo-ui`. Detection rules, server contracts, and Ryan’s vision service were not changed.

## Four-screen workflow

The primary tabs are Prepare, Monitor, Results, and Library.

1. **Prepare.** Two entry points come first: **Six-well procedure** and **Write a protocol**. The six-well draft remains editable. Instruction and observation stay on the step card. The source quote, duration, and missing-information questions stay inside the card details. A question count shows when questions exist. Save and approve stay with the draft, and **Set up monitoring** stays with an approved six-well version. Prepare does not publish. Local drafts stay labeled as saved in this browser.
2. **Monitor.** The live picture fills the left side. The right side keeps the current decision above a chronological evidence list. Setup offers **Six-well monitoring** or **Three-cup capture**. Six-well behavior is unchanged. Three-cup capture records the camera and optional operator markers. It hides the six-well overlay, does not run the six-well detector, and shows “Capture mode — automatic checks not connected.” The right panel keeps a short observation, the approved procedure, and an evidence list. Longer notes stay inside details. Setup selects one approved procedure for the run: RED → BLUE then GREEN → RED, or BLUE → RED then GREEN → BLUE. Opening a local review file or starting capture freezes that choice, and a later control change does not rewrite the session. An older session with no stored choice remains the first procedure. The demo plan to perform GREEN → BLUE is setup guidance for the first procedure only. It is not an approved step and it is not sent to an observation model. Extra and out-of-order person reports stay in the evidence list and do not complete a step. A local recording plays on the stage without upload. A file over the 80 MiB shared-library limit stays on disk; the page says to review it locally, publish the notes without the video, or use a smaller file. Evidence watches a recording-relative time when that time is inside the loaded file. A time before the recording, missing metadata, or a playback failure is shown. The detector is not connected, and no observation request is sent. Cup names are the physical labels RED, GREEN, and BLUE. Markers say what a person reports. They do not complete steps or claim a camera judgment. **Download recording** and **Download annotations** stay with that take. The annotation file is review data, not a Laya training set. **Record 12-second timestamp check** draws a changing clock through the same recorder so duration and seeking can be checked. The large picture stays on the left. The right panel shows the current action, one issue, and one next step. Setup is one guided sequence: start the camera, position the regions, calibrate, preview, then start monitoring. Earlier steps stay reachable. The camera being open is not treated as a calibrated reading. Missing calibration and unknown previews are stated beside those steps. **Record this run** is optional and is chosen before monitoring starts. It records the camera without audio, shows **Recording**, and stops when monitoring stops. A recording error or a camera disconnect stops the recording only. The analyzer keeps running. The file stays in this browser until publication. Demo and imported video stay inside Setup, closed until requested. An imported file is attached only after **Attach this file to the run**. A synthetic sequence stays labeled synthetic and does not create a camera recording. Pause-on-issue remains synthetic-only. Stop camera and Stop monitoring stay beside the clock while they apply. **Finish session** is a separate action after monitoring stops. It writes `finishedAt`. Stopping the camera, saving an event, or leaving the tab does not finish the session. Finished does not mean the run succeeded. Setup collapses while a run is in progress. An observed correction is shown briefly, then the panel returns to the current action. History, measurements, and session identifiers stay in expandable sections.
3. **Results.** Opening Results loads saved monitor sessions from the library. It keeps the session already selected in this browser, including one opened by ID. If this browser has just monitored a session and nothing else is selected, that session stays selected even when a newer session exists. The newest shared session is used only when this browser has no selection. Previous sessions lists protocol title, time, source, and stored status. The loaded record shows issues, observed corrections, human reports, and the frozen protocol association. A finished session with an approved procedure can be published from a preview. If a local recording is present, the preview plays it and **Include recording** shows its size against the 80 MB limit. Publishing without a recording still works. A failed upload keeps the local file and offers retry or an explicit publish without the recording. Unresolved issues stay visible and do not block publication. **Publish** is an explicit click. **View in Library** opens that publication. Evidence and history stay expandable. The session ID stays behind Details. It does not treat frame metadata as footage, does not request a Gemini explanation, and does not fill an empty list with synthetic examples. Colored-water review records stay separate.
4. **Library.** Search published titles, sort newest or oldest, and open one snapshot. The table adds a record label: recorded experiment, synthetic demonstration, or protocol only. A recorded publication shows the frozen procedure, observations, unresolved deviations, observed corrections, human reports, evidence, and notes. When a recording was included, the page plays that shared file and offers **Watch moment** only for an alert whose run time falls inside the recording. The source label stays visible. A missing recording is described as not included. Observation timestamps stay under Details. **Repeat experiment** creates a planned replication with the frozen procedure and no copied observations. **Set up monitoring** appears only when that procedure is the supported six-well order.

## Where former tabs moved

- **Review** moved into Results as colored-water review records. Saving a review copy, human reports, and the grounded explanation stayed with that record type.
- **Footage** moved into Results under Reference analysis.
- **Library** is a primary tab again. Browsing, search, and opening a publication happen there. Publishing a performed run stays in Results. Older protocol-only publications remain readable. A replication is still a plan until its own execution screen is started. The shared library is the database on this network, not a public website, and it does not sign anyone in.
- **Record** stayed the replication execution screen, opened from a replication record in Library. It is not a primary tab and it is not treated as a monitor session.
- **Synthetic monitor demos** stayed under Monitor Setup. Authored review fixtures stayed behind Authored examples and are not the default results.
- **Storage / session id** stayed expandable on Monitor. Results reads the same saved monitor session when the library returns it.

## What is connected

Prepare’s extract, save, and approve calls are the existing ones. **Six-well procedure** loads an editable draft with Fill A1 through Fill B3 and no durations. After that version is approved, **Set up monitoring** opens Monitor with the title and version. It does not start the camera. Each new monitor session stores that approved snapshot as `preparedProtocol`. Later edits to the draft do not change the stored copy. Other approved protocols stay in Prepare and cannot start this path.

`POST /monitor-sessions/:id/finish` sets `finishedAt` once. A later event is rejected. `POST /monitor-sessions/:id/publish` copies the finished session into one experiment. A retry returns that same publication and does not rewrite it. The copy includes the procedure, observation states, alerts, human reports, evidence labels, the recording offset, and optional notes. Video bytes are not stored in that document. An included recording is a separate GridFS file, referenced by `sharedMediaId`, with a limit of 80 MB. `runStartOffsetMs` is the recording position of run time zero, so a recording that starts later than monitoring is not treated as the same clock. Synthetic sessions are stored as `kind: demonstration` and have no camera recording. Camera and imported video are `kind: recorded`. Older `POST /experiments` publications stay `kind: protocol`.

Library lists publications from `GET /experiments` with a title search, newest or oldest order, and pages of 20. Opening one loads that snapshot and, when present, the copied run. **Repeat experiment** creates a planned replication. The execution screen is opened from that record.

Monitor still writes the in-memory review record and, separately, the Atlas monitor session. Results lists those saved sessions from the library and reads the frozen instructions beside the one that is opened. A replication is reached only from its publication.

## Remaining disconnected or unsupported records

- Gemini preparation does not turn an arbitrary protocol into camera monitoring.
- A monitor session cannot be sent to the review explanation endpoint. No explanation is invented for it.
- A monitor session with only frame metadata is not played as video.
- A physical webcam was not used to verify recording. The recording path was checked with a generated file and the library API.
- A failed upload can leave an unreferenced GridFS file. The publication is not created, and the browser file remains.
- Legacy review runs, monitor sessions, and replications are not converted into one another.
- Real camera footage is still unvalidated. A high mix score still means unknown, not a hand or pipette.
- The production build does not proxy `/library`. Use the Vite dev server with the library on `127.0.0.1:8788`.
- The Monitor can ask the local library at `POST /clip-observations` to check one selected clip. That request carries clip times only: `sessionId`, `videoId`, `requestId`, `clipStartMs`, `clipEndMs`, and `sourceOffsetMs` equal to the clip start. It does not upload the recording and it cannot run the adapter, because the adapter needs the clip bytes from a server-side file path. With the authorization gates closed, the route returns `awaiting-authorization` and `remoteCallMade: false`. **Import adapter result** reads a saved adapter JSON on this computer and posts it to `POST /clip-observations/reviews`. The review checks `sessionId`, `videoId`, request identity, clip duration, and `sourceOffsetMs`. It keeps the raw document and `needsHumanVerification`. It does not call the adapter and it does not rewrite the adapter ids. Those ids can differ from the Monitor session. Events stay off the evidence list until **Link this result to this recording**. That link is stored separately. A supplied manifest `sourceSha256` or `sourceSha256AfterEncoding` is checked against the selected file; a mismatch is not linked. Without a source hash, the same button is an explicit confirmation and the details say user-confirmed, with the original ids visible. The clip window and evidence times must fall inside the selected recording’s duration. Switching recordings drops the link. Synthetic model ids are labeled synthetic fixtures, not observations. Evidence times are already original-media milliseconds. Watch seeks the open recording at that time and does not add `sourceOffsetMs` again. Person reports stay in the protocol comparison, which uses the frozen procedure for the recording. A newer request replaces an older one. Negative times, reversed intervals, zero-length intervals, evidence outside the clip, and identical cups are rejected. Evidence inside the clip but outside its event stays uncertain and is not seekable. `no_transfer` and `unavailable` stay distinct.
- The verified development clip is `C:/Users/rupes/Projects/labbench-codex-offline/server/three-cup-offline/local/integration/recording-1-review-84000-92000.mp4` (4,065,561 bytes, 8,000 ms, `sourceOffsetMs` 84000, session `local-review-recording-1`, video `recording-1`). A future authorized invocation has to run on the server, with both gates open, and pass that path as `clipPath` to `adapterArguments` / `finishClipCheck`. The browser cannot supply the path. Leave `THREE_CUP_CLIP_AUTHORIZED` unset on the library. Seek the original recording, not only the trim: returned times already include the 84000 ms offset. The trim’s frame grid is about 10 ms off the source.
- The captured disabled-adapter response is `adapter-disabled-response.json` beside that clip. Imported, it is unavailable / `remote_disabled`, with `remoteCallMade: false` and `latencyMs: null`.
- Ryan’s adapter commit verified by Codex is `119e048931069b817eb7e3a14b4f6d860a050ef5` on `three-cup-vision-pilot`. It was not merged, and this app does not call it. Codex’s offline probes at that commit passed the earlier zero-duration, out-of-event evidence, out-of-video appearance, and NaN sampling cases. The app still rejects a zero-length event and evidence outside the requested clip, and it keeps evidence that misses its event uncertain with seeking disabled. The OpenCV package still compares only RED → BLUE then GREEN → RED and does not detect pours.

## Synthetic demo notes

Pause demo when an issue appears is on by default inside Setup and applies only to synthetic playback. Continue demo does not acknowledge or correct. Replay clears the pause and starts a new session. Source timestamps stay one 220 ms step per frame. Slow playback changes only the wall clock.
